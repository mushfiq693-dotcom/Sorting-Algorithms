# PHASE 4 — Beginner Learning Path + Code Debugger + Bug-Hunt Challenge

> **Standalone add-on.** Give this to Claude Code as its own prompt, any time after Phase 1–3
> are working. It builds on the existing visualizer/state architecture — do not rebuild it.
> Paste the "GLOBAL CONTEXT" block from the original prompt file first if starting a fresh
> session, so Claude Code has the project context.

---

## Goal

Two things beginners currently don't get from the visualizer alone:
1. A **guided path** that tells them what order to learn things in and why, instead of dropping
   them into 5 algorithms with no starting point.
2. A way to see code **execute like a real debugger** — actual variable values changing line by
   line — plus a way to actively test their understanding by finding and fixing bugs.

Build these as two connected features: **Learning Path** (documentation/guidance layer) and
**Code Debugger + Bug Hunt** (interactive layer). They should link into each other — the Learning
Path recommends when to try the debugger and when to try a bug hunt for each algorithm.

---

## PART A — Beginner Learning Path

### A1. Learning Path page (`app/learn/page.tsx`)

A dedicated route, linked from the landing page and nav, that lays out a **recommended order**
with a short reason for each step. Don't just list the 5 algorithms — sequence them by conceptual
difficulty:

```
1. Bubble Sort     → "Start here. Simplest possible mechanism: compare neighbors, swap if wrong order."
2. Selection Sort  → "Same difficulty tier, different strategy: find-the-minimum instead of swap-as-you-go."
3. Insertion Sort  → "Introduces shifting instead of swapping. Closest to how humans sort by hand."
4. Merge Sort      → "First recursive algorithm here. Introduces divide-and-conquer thinking."
5. Quick Sort      → "Builds on Merge Sort's recursion, adds the harder idea of in-place partitioning."
```

Each step in this path is a card showing:
- Algorithm name + one-line "why this order" reasoning (as above)
- Estimated time to understand (e.g. "~15 min")
- A visual completion checkmark once the user has viewed that algorithm's page (track in
  local component state — no backend/auth needed)
- A "Start" button linking to that algorithm's page

### A2. Per-algorithm learning structure

On each algorithm's existing page (`app/algorithms/[algorithm]/page.tsx`), reorganize the existing
content (mechanism, visualization, code, complexity — all already built in Phase 1/2) into a
**progressive disclosure layout** instead of showing everything at once:

```
1. The Idea       — one paragraph, plain English, no code, no jargon. Use a real-world analogy
                     where it genuinely helps (already have "cards in hand" for Insertion Sort —
                     add similarly honest analogies for the others, or skip the analogy if forcing
                     one would be misleading).
2. Watch It Work  — the existing visualizer, pre-loaded with a small (~8 element) example array
                     so beginners aren't overwhelmed by a 30-bar array on first view.
3. Read the Code  — the existing CodeViewer, now with a plain-English comment beside each
                     logical block (not every line — group into meaningful chunks: "outer loop",
                     "inner comparison", "swap logic").
4. Why It's Fast/Slow — the existing complexity card, but add ONE sentence explaining *why* the
                     complexity is what it is in terms of what the code is doing (e.g. "Two nested
                     loops, each up to n times, means roughly n × n = n² comparisons in the worst case").
5. Try It         — links to both the Debugger (Part B) and, if available for this algorithm,
                     the Bug Hunt (Part B) for hands-on practice.
```

Use a simple stepper/tab UI (numbered 1–5) so beginners aren't shown a wall of content — but allow
jumping to any step freely, don't force linear progression (this is a documentation aid, not a
gate).

### A3. Terminology glossary

Add a small, persistent glossary component (e.g. a slide-out panel or hover-tooltip system)
covering terms used across the explanations: *comparison, swap, in-place, stable, time complexity,
space complexity, recursion, base case, pivot, partition, divide and conquer, subarray*. Each term:
one-sentence plain definition, no circular jargon (don't define "recursion" using the word
"recursive").

## PART B — Code Debugger (step-by-step execution with live variables)

### B1. Debugger view (`components/debugger/CodeDebugger.tsx`)

A new mode on the algorithm page — toggle between "Visualizer" (existing bars view) and
"Debugger" (this new view). The Debugger view shows:

- The C++ code (reuse existing `CodeViewer`) with the **current line highlighted**, same sync
  mechanism already built in Phase 1.
- A **live variables panel** beside the code showing the current value of every in-scope variable
  at this exact point in execution (e.g. for Bubble Sort: `i`, `j`, `n`, `swapped`, and the full
  `arr` array with the currently-touched indices marked).
- A **call stack panel** for the recursive algorithms (Merge Sort, Quick Sort) showing the current
  chain of recursive calls with their arguments (e.g. `mergeSort(0, 7)` → `mergeSort(0, 3)` →
  `mergeSort(0, 1)`), so beginners can see recursion depth and unwinding, not just the flat
  operation list.
- Step controls: **Step Into** (advance one operation), **Step Back** (go to the previous operation
  — requires keeping the full operation history navigable both directions, not just forward),
  and **Run to Completion**.

### B2. How this connects to the existing operation engine

Do **not** build a second execution engine. The existing `SortOperation[]` array already produced
by each algorithm function (Phase 1/2) is the source of truth. For the debugger:
- Extend the operation-to-line mapping (already built in Phase 1 for code sync) to also capture a
  **variable snapshot** at each operation — add an optional `snapshot` field to each operation, or
  maintain a parallel array of snapshots indexed the same way as operations. Populate this inside
  each algorithm function as it runs (e.g. record `{i, j, n, swapped}` at the moment of each
  `compare`/`swap` operation).
- Step Back is just moving the existing `currentOperationIndex` backward and re-rendering the
  snapshot + array state at that index — do not re-run the algorithm.
- For recursive algorithms, the call stack display comes from tracking recursion entry/exit as
  additional lightweight operations (e.g. `{ type: "call-enter", fn: "mergeSort", args: [0,7] }` /
  `{ type: "call-exit", fn: "mergeSort" }`) alongside the existing compare/swap/merge operations —
  extend the shared `SortOperation` type with these two variants.

### B3. Explanation tie-in

Below the variables panel, one line in plain English describing what this exact line does *in
context* (not a generic description — reference the actual current variable values), e.g.:
> "Since `arr[j]` (5) is greater than `arr[j+1]` (3), the condition is true — the swap on the next
> line will execute."

## PART C — Bug Hunt Challenge

### C1. Concept

For each algorithm, provide 2–3 **pre-written buggy variants** of the C++ code (off-by-one errors,
wrong comparison operator, wrong loop bound, missing swap, etc. — realistic beginner mistakes, not
absurd/obviously-broken code). The user's job: find which line is wrong and fix it.

### C2. UI flow (`components/challenge/BugHunt.tsx`)

1. Present the buggy code (same CodeViewer component, editable mode) alongside the visualizer.
2. User can run the buggy code through the existing visualizer/operation-engine — since the engine
   works on real logic, running genuinely-buggy logic must actually produce a genuinely-wrong
   sort. **This means the buggy variants must be implemented as real alternate TypeScript functions
   in `src/algorithms/[name]Buggy.ts`**, not simulated — the visual wrongness (array ending up
   unsorted, or an infinite-loop guard triggering) must come from actually running the flawed logic.
3. User identifies the buggy line by clicking it, then edits it inline (a simple text edit on that
   line, not a full code editor) and re-runs to verify their fix produces a correctly sorted array.
4. Feedback:
   - Correct line identified + correct fix → "🎉 Fixed! Here's what was wrong: [plain-English
     explanation of the bug's effect]."
   - Wrong line identified → gentle nudge, e.g. "That line looks right — check the loop boundary
     condition instead." (Give a hint pointing at the right *region*, not the exact line, so it's
     still a puzzle.)
   - Correct line but wrong fix → "Right line! But this fix doesn't produce a correct sort — try
     running it to see why." (let them observe the still-wrong output rather than just telling them)
5. Track per-session: attempts, hints used, bugs fixed — show a simple summary at the end, no
   scoring/leaderboard needed.

### C3. Example bugs to seed (write real code for these, one per algorithm minimum)

- **Bubble Sort:** inner loop condition `j < n` instead of `j < n - i - 1` (causes index-out-of-bounds
  or redundant comparisons — pick the version that fails cleanly)
- **Selection Sort:** comparison `arr[j] <= arr[minIdx]` instead of `<` (still sorts correctly but
  breaks stability — good for teaching *why* stability matters, not just "found the bug")
- **Insertion Sort:** `while (j >= 0 && arr[j] >= key)` instead of `>` (same stability lesson)
- **Merge Sort:** merge condition `arr[i] < arr[j]` instead of `<=` (subtle stability bug)
- **Quick Sort:** partition loop `j <= high` instead of `j < high` (includes pivot in comparison,
  causes incorrect partition)

Use at least one bug per algorithm that causes a **visibly wrong sort** (not just a subtle
stability issue) so beginners get a satisfying "aha, I see it's wrong" moment before the subtler
stability-related bugs.

## Definition of done for Phase 4

- Learning Path page exists, sequences all 5 algorithms with clear reasoning, tracks completion
  per algorithm in-session.
- Each algorithm page has the 5-step progressive structure (Idea → Watch → Code → Why → Try),
  freely navigable.
- Glossary accessible from any algorithm page.
- Debugger mode works for all 5 algorithms: live variables update correctly at every step, Step
  Back works without re-running the algorithm, call stack panel shows accurate recursion state for
  Merge Sort and Quick Sort.
- Bug Hunt has at least one real (not simulated) buggy variant per algorithm, produces genuinely
  incorrect output when run, and correctly validates user fixes by re-running the corrected logic.
- No new execution engine duplicated — debugger and bug hunt both reuse the existing
  `SortOperation` pipeline from Phase 1/2.
- Test the debugger's Step Back specifically at the very first and very last operation (boundary
  conditions) to confirm it doesn't break.
