Use Supabase as the backend platform.

The architecture should use:

* Supabase Auth
* PostgreSQL
* Row Level Security (RLS)

Environment variables should remain:


Before adding or changing anything here, confirm against the Section 1 audit whether these already
exist and are populated — do not overwrite a working existing connection, and do not assume fresh
setup is needed without checking first.

Never hardcode credentials.

Never expose a service-role key to the browser.

Never place secrets in client-side code.

# 4. DESIGN THE DATABASE BEFORE IMPLEMENTING IT

Based on the repository audit, design the required PostgreSQL schema.

For each table determine:

* purpose
* primary key
* foreign keys
* nullable/non-nullable fields
* unique constraints
* indexes
* timestamps
* relationships
* delete/update behavior — explicitly decide, per table, whether related rows should
  `CASCADE DELETE`, be prevented from deletion while dependents exist (`RESTRICT`), or have the
  foreign key nulled out (`SET NULL`) when a parent row (especially a user) is deleted; don't leave
  this as an unstated default
* whether the table is user-owned or public
* whether the table requires RLS

Prefer normalized relational design.

Avoid:

* unnecessary duplication
* giant JSON blobs when relational fields are appropriate
* redundant user information
* storing authorization decisions in client state
* unnecessary tables
* unnecessary abstractions

Use PostgreSQL constraints wherever possible instead of relying only on frontend validation.

# 5. USER PROFILE ARCHITECTURE

Supabase Auth's:

```text
auth.users
```

must remain the authentication source of truth.

Do NOT duplicate the authentication system.

Create/use an application-level profile table only where necessary.

The profile identity should be strongly linked to:

```text
auth.users.id
```

The profile architecture must support at minimum:

```text
role
status
created_at
updated_at
```

Use the following Beta authorization model unless the existing architecture clearly requires a
safer equivalent:

### Roles

```text
student
admin
```

### Account/Beta status

```text
pending
approved
rejected
suspended
```

New users must NOT be able to choose their own role or Beta status.

Default new-user state should be:

```text
role   = student
status = pending
```

The client must never be trusted to determine authorization.

# 6. PROFILE CREATION

Implement a secure mechanism so that when a new Supabase Auth user is created, the corresponding
application profile is automatically created.

The mechanism must ensure:

* the authenticated user's identity comes from Supabase Auth
* role cannot be supplied maliciously by the client
* status cannot be supplied maliciously by the client
* default role is `student`
* default status is `pending`

Handle failure cases carefully.

Do not create duplicate profiles.

Use appropriate uniqueness/primary-key constraints.

---

# 7. ROW LEVEL SECURITY

RLS is a **mandatory security boundary**.

Do NOT rely on:

* React conditionals
* hidden buttons
* client-side role checks
* Zustand state
* localStorage
* middleware alone
* URL protection alone

for database security.

Every user-facing table must be evaluated for RLS requirements.

For each table explicitly determine:

### SELECT

Who can read?

### INSERT

Who can create?

### UPDATE

Who can modify?

### DELETE

Who can delete?

Use the principle of least privilege.

---

# 8. USER PROFILE SECURITY

A normal student should be able to access only the profile information they are authorized to
access.

A normal user must NOT be able to modify:

```text
role
status
```

through normal client-side operations.

A malicious request such as:

```text
UPDATE profiles
SET role = 'admin'
```

must fail for a normal user.

Likewise:

```text
UPDATE profiles
SET status = 'approved'
```

must fail for a normal user.

Authorization must be enforced at the database/security layer.

---

# 9. ADMIN ACCESS

The Beta architecture must support an admin-controlled approval system.

Admins should eventually be able to:

* view pending users
* approve users
* reject users
* suspend users
* restore eligible users
* manage appropriate platform data

But do NOT automatically give every authenticated user admin privileges.

Admin authorization must be securely determined.

Do not trust:

```text
localStorage
```

or:

```text
role stored in frontend state
```

or:

```text
query parameters
```

or arbitrary request bodies.

## 9.1 BOOTSTRAPPING THE FIRST ADMIN

Because no user can grant admin access if no admin exists yet, this needs an explicit, deliberate
mechanism rather than being left unspecified:

* Create a **one-time seed script** (e.g. `scripts/seed-admin.ts` or a dedicated seed migration)
  that promotes a specific, explicitly-provided user (identified by email or user ID that I supply
  at run time — never hardcoded into a committed file with real credentials) to `role = admin` and
  `status = approved`.
* This script must only be runnable with direct database/service-role access (i.e. it's an
  operator-run script, not an exposed API route or client-callable function) — it must NOT be
  reachable from the deployed application in any form.
* Document the exact command I need to run to bootstrap the first admin after this task is
  complete, since I'll need to do this once manually after deployment.
* Do not create any other mechanism (env var flag, magic first-signup-becomes-admin logic, etc.)
  that could let the first admin be established implicitly or automatically — this must be a
  deliberate, auditable, manually-triggered action.

## 14.1 ROLLBACK STRATEGY

For every migration created in this task:

* Provide a corresponding **down/rollback migration** (or, if the project's migration tooling

* If a migration fails partway through application, explain what state the database would be left

# 19. ABUSE PREVENTION (SIGNUP / PENDING-REQUEST RATE LIMITING)

Because this is a restricted, invite/approval-based beta, consider basic abuse prevention at the
database/application boundary — not full production-grade rate-limiting infrastructure, but
reasonable guardrails appropriate for a beta:

* Prevent a single email/user from creating multiple `pending` profile rows (should already be
  naturally prevented if profile creation is tied 1:1 to `auth.users.id`, but confirm this
  explicitly rather than assuming it).
* Consider whether Supabase Auth's built-in signup rate limiting is sufficient for beta scale, or
  whether an additional lightweight guard (e.g. a simple check on repeated signup attempts from
  the same source in a short window) is justified — do not build a custom rate-limiting system
  from scratch unless the existing architecture has nothing usable; prefer Supabase's built-in
  protections first.
* This is explicitly scoped to **basic guardrails appropriate for a department-restricted beta**,
  not enterprise abuse-prevention — do not over-engineer this.
