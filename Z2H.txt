## Goal

Turn the site into a genuine **zero-to-advanced course**, not just an algorithm-by-algorithm demo:
- A structured documentation section that goes from "what is sorting" up to advanced analysis of
  these same 5 algorithms (no new algorithms — deeper treatment of the existing 5).
- Bangla explanations layered in specifically where concepts get hard, alongside the English base
  (not a full translated site — targeted bilingual support).
- Three new practice modes: **Quiz**, **Coding Practice**, **Prediction Exercises** — in addition
  to the existing Bug Hunt from Phase 4.

## PART A — Documentation Structure (Zero → Advanced)

### A1. New `/docs` section (`app/docs/[...slug]/page.tsx` or similar nested routing)

Organize as a proper course with levels, not a flat page list:

```
LEVEL 0 — Before You Start
  - What does "sorting" mean, formally? (input, output, ordering relation)
  - What is a comparison? What is a swap? Why do we count them?
  - Reading Big-O notation for absolute beginners (no math background assumed)
  - How to read the C++ used on this site (vector, reference params &, basic syntax notes for
    people coming from other languages or no language)

LEVEL 1 — The Simple Algorithms (maps to existing Bubble/Selection/Insertion pages)
  - Each existing algorithm page, linked in from here with a short abstract

LEVEL 2 — Divide and Conquer (maps to existing Merge/Quick pages)
  - A dedicated conceptual page BEFORE Merge Sort: "What is recursion?" with a simple non-sorting
    example first (e.g. factorial or countdown) before applying it to sorting
  - Then Merge Sort, then Quick Sort, each linked in with abstract

LEVEL 3 — Advanced Analysis (new content, deep dive on the SAME 5 algorithms — no new algorithms)
  - Formal proof sketch of why Bubble/Insertion are O(n²) — actually count the comparisons
  - Why Merge Sort is ALWAYS O(n log n) regardless of input (unlike Quick Sort) — derive it from
    the recursion tree (log n levels, n work per level)
  - Why Quick Sort degrades to O(n²) — walk through the already-sorted-array worst case concretely
    with the exact partition calls that cause it
  - Stability formally defined + proof sketch of which of the 5 are stable and why (trace through
    what happens to equal-value elements in each algorithm's actual logic)
  - In-place vs not: why Merge Sort needs O(n) auxiliary space and the others (mostly) don't
  - Brief mention (2-3 sentences, not full implementation) of hybrid real-world approaches like
    Timsort or Introsort, framed as "here's how production sorting actually combines these ideas"
    — informational only, not another algorithm to implement/visualize

LEVEL 4 — Choosing the Right Algorithm
  - Decision guide: given constraints (data size, memory limits, stability need, nearly-sorted
    data), which of the 5 to reach for — can reuse/expand the existing Compare page (Phase 3)
    content here in fuller prose form
```

### A2. Docs sidebar navigation

A collapsible tree nav (Level 0 → 4, expandable) always visible on `/docs/*` routes, showing
progress (which pages visited) similar to the Learning Path checkmarks from Phase 4 — reuse that
same completion-tracking pattern, don't build a second one.

### A3. Content format

Each docs page: prose explanation (not just bullet dumps), inline diagrams/code snippets where
they clarify (reuse existing `CodeViewer` and any existing diagram components), and a "Try it in
the Visualizer" link at the bottom of pages tied to a specific algorithm, jumping straight to that
algorithm's page.

## PART B — Bangla Explanations for Complex Concepts

### B1. Scope — NOT a full site translation

Do not translate the entire site. Add Bangla explanations **only** at points where concepts are
genuinely hard for beginners:
- Recursion (Level 2 intro page)
- Divide and conquer generally
- Big-O / time complexity reasoning (Level 0 and Level 3 pages)
- Why Merge Sort's complexity is guaranteed but Quick Sort's isn't
- Stability (the concept itself, and why it matters)
- Space complexity / in-place vs auxiliary space

### B2. Implementation

- A small toggle component (`components/docs/BanglaNote.tsx`) — a collapsible "বাংলায় বুঝি 🇧🇩"
  box inserted directly under the English explanation at each of the points listed in B1. Collapsed
  by default, expandable, so it doesn't clutter the page for readers who don't need it.
- Bangla text should be **written fresh in natural Bangla**, not a literal/mechanical translation
  of the English paragraph — explain the same concept the way a Bangla-speaking teacher would,
  using simple analogies where helpful (e.g. explain recursion via "একটা কাজ নিজের ছোট ভার্সন দিয়ে
  সমাধান করা" style framing, not word-for-word English-to-Bangla conversion).
  - I'll review and can help refine the actual Bangla wording — write a reasonable first draft
    for each of the concepts listed in B1, and flag clearly in code comments which are drafts I
    should review, so I know which ones to check before treating them as final.
- Do not use Google-Translate-style output — if a natural, clear Bangla explanation can't be
  written confidently, leave the box with an English explanation and a note that Bangla is coming,
  rather than shipping a low-quality mechanical translation.

## PART C — Practice Modes

### C1. Quiz Mode (`components/practice/Quiz.tsx`)

- Placed at the end of each algorithm's Level 1/2 page AND at the end of each Level 3 advanced page.
- 4-6 multiple-choice questions per placement, mixing:
  - Conceptual (e.g. "Which of these is true about Bubble Sort's best case?")
  - Trace-based (show a small array state mid-algorithm, ask "what happens next?")
  - Complexity (e.g. "What is Merge Sort's worst-case time complexity?")
- Immediate feedback per question (correct/incorrect + one-sentence explanation of the right
  answer, not just a checkmark).
- No login/backend — track quiz completion/score in-session only (same pattern as existing
  completion tracking), reset on page reload is acceptable.
- Write real, algorithm-accurate questions — do not generate generic/filler questions; each
  question must test something actually explained on that specific page.

### C2. Prediction Exercises (`components/practice/PredictNext.tsx`)

- Available from each algorithm's "Try It" section (alongside links to Debugger and Bug Hunt from
  Phase 4).
- Flow: show the visualizer paused at a specific mid-algorithm state (a real state pulled from the
  actual `SortOperation` array at some index, not a fabricated one), then ask the user to predict
  the **next operation** — e.g. "Which two elements will be compared next?" (click two bars) or
  "Will a swap happen?" (yes/no).
- After the user answers, step the visualizer forward one operation for real and show whether the
  prediction was correct, with a one-line explanation referencing the actual algorithm logic at
  that point.
- Offer several rounds (5-8 predictions) per session, pulling from different points in the
  operation sequence (early/mid/late in the sort) so it's not always the same trivial first
  comparison.
- Reuses the existing operation engine and `currentOperationIndex` stepping mechanism from
  Phase 1/2 — do not build a separate simulation for this.

### C3. Coding Practice (`components/practice/CodingPractice.tsx`)

- For each of the 5 algorithms, a practice screen where the user writes the sort logic themselves
  in a simple code editor (use a lightweight in-browser editor — e.g. CodeMirror or Monaco via a
  thin wrapper; pick whichever integrates more simply with the existing stack, avoid adding heavy
  unnecessary dependencies beyond what's needed for the editor itself).
- Language: **TypeScript**, matching the shape of the existing algorithm engine functions (i.e.
  the user implements `function bubbleSort(arr: number[]): number[]` or similar), NOT C++ — this
  keeps auto-checking simple and consistent with the existing engine, since the existing engine is
  already TypeScript-based.
- Provide a starter stub with the function signature and a comment describing the task, but no
  filled-in logic and no giveaway structure that trivializes the exercise.
- **Auto-check on submit:**
  - Run the user's function against a fixed set of test arrays (random, sorted, reverse-sorted,
    duplicates, single-element, empty — same categories used for correctness testing elsewhere in
    this project) and confirm the output is correctly sorted for each.
  - Report which test cases passed/failed clearly, without giving away the fix.
  - If all pass, show a success state and (optionally) a brief comparison against the reference
    implementation's approach — not to shame a different-but-valid approach, just to show one way
    it's commonly done.
  - Do not silently accept an incorrect implementation and do not fabricate a "passed" result —
    actually execute the user's code against the test arrays.
- Sandbox the execution safely (the user's code should not be able to affect the rest of the app —
  run it in a scoped function context, avoid `eval` on unsanitized input where a safer alternative
  like `new Function(...)` with restricted scope is available; if full sandboxing isn't practical
  client-side, at minimum wrap execution in a try/catch with a timeout guard against infinite loops
  so a broken submission can't hang the page).
