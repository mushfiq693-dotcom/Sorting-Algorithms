1. ISSUE DESCRIPTION & THREAT MODEL (BEFORE FIX)
================================================================================

Previous Vulnerability:
  In `src/components/practice/CodingPractice.tsx`, user-submitted JavaScript/
  TypeScript was executed directly on the browser's main UI thread using `new Function()`.

Threat Vectors:
  1. Denial of Service (UI Freeze): If a student wrote an accidental infinite loop
     (e.g., `while(true)` or `while(i < n)` without incrementing `i`), the main
     JavaScript UI thread would lock up permanently, freezing the browser tab.
  2. Main-Context Execution: The function had access to the main window's execution
     context without isolation.

================================================================================
2. ARCHITECTURAL SOLUTION & IMPLEMENTATION DETAILS
================================================================================

Solution Summary:
  All user-submitted algorithm code execution has been completely offloaded from
  the main React thread into an isolated Web Worker created dynamically via inline
  Blob URLs (`new Worker(blobUrl)`), governed by a strict 1000ms timeout guard.

Key Capabilities Implemented:
  1. Isolated Thread Execution: Code runs in a dedicated background worker thread,
     ensuring the React UI remains smooth and responsive at all times.
  2. Strict 1000ms Execution Timeout: Automatically terminates any script that exceeds
     1000ms and returns a controlled timeout error banner without locking the tab.
  3. Automatic Worker Lifecycle Cleanup:
     - On completion: Worker is terminated (`worker.terminate()`) and Blob URL is revoked.
     - On re-submission/reset: Any active in-flight worker is terminated immediately.
     - On component unmount: `useEffect` cleanup hook guarantees all workers are killed.
  4. TypeScript & JavaScript Compatibility: Added lightweight type-annotation
     stripping (`stripSimpleTsTypes`) so students can write pure TypeScript or JavaScript.
  5. Zero Backend Dependencies: 100% browser-native Web Worker sandbox; works
     seamlessly across Next.js static, SSR, and client environments.

================================================================================
3. TIMEOUT & CLEANUP MECHANICS
================================================================================

How the Timeout Works:
  1. `executeCodeInWorker` launches a new `Worker(blobUrl)` and arms a `setTimeout` for 1000ms.
  2. If the worker returns results within 1000ms, the timer is cleared and results are rendered.
  3. If the worker exceeds 1000ms (infinite loop / recursion freeze):
     - Timer callback invokes `worker.terminate()` immediately.
     - Object URL is revoked via `URL.revokeObjectURL(blobUrl)`.
     - Returns controlled error: "Execution timed out (1000ms limit exceeded)..."

Worker Cleanup Guarantees:
  - Success State: Worker terminated immediately after posting message.
  - Failure/Error State: Worker terminated immediately upon runtime/syntax error.
  - Timeout State: Worker terminated forcefully on timer expiration.
  - Component Unmount: `activeWorkerRef.current.terminate()` called in useEffect cleanup.
